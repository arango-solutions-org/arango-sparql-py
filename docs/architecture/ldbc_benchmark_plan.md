# LDBC SNB benchmark — research & implementation plan

**Status:** Proposed — awaiting maintainer review
**Date:** 2026-10-23
**Implements:** [`PRD.md`](./PRD.md) §13.6 (LDBC SNB benchmark)
**Work packages:** `WP-LDBC-*` (tracked in [`implementation_plan.md`](./implementation_plan.md))
**Sister plan:** `arango-cypher-py/docs/ldbc_benchmark_plan.md` (same date, same
structure). This plan mirrors it section for section, and states where the
SPARQL side has to differ and why.

> These are not LDBC Benchmark Results. This plan uses the LDBC Social Network
> Benchmark (SNB) data generator output and reference SPARQL queries as a
> validation and performance corpus. It is not an implementation of an LDBC
> Benchmark, and no number it produces is an audited result. (See §2.6.)

---

## 1. Why

Today the translator has four kinds of evidence:

- Golden fixtures (`tests/translate/*.yml`) pin exact AQL.
- The W3C DAWG suite measures language coverage on tiny graphs.
- The `pyoxigraph` cross-validation (`tests/cross/`) compares bindings on
  hand-built datasets, executed by the AQL-subset interpreter.
- The live integration tests run against small seeded databases.

None of them exercises **realistic multi-hop SPARQL written by someone else**
against a **graph of millions of triples**, in **all three physical layouts**,
at sizes where **performance is measurable**.

LDBC SNB fills that gap:

- It has a published SPARQL reference implementation: 21 read queries written
  for GraphDB by the LDBC task force (Apache-2.0).
- The same graph is published as Turtle, so the RDF layout is native, not
  derived.
- It has a property-graph schema that the PG and LPG layouts can follow, the
  same schema the sister project uses.
- LDBC publishes expected results for it, an oracle independent of both
  `pyoxigraph` and us.

It serves the three goals:

- **validate** the translator;
- **detect and fix** defects, especially silent ones;
- **measure performance** across the RDF (RPT), LPG and PG layouts.

### 2.2 How the SPARQL reference is written

- **Parameters** are spliced in as text: `%personId%` is replaced by the
  driver (`GraphDBQueryStore`, separator `%`). The reference is therefore not
  bind-parameterised.
  - Entity IDs are zero-padded to 20 digits: `sn:pers00000000000000000933`.
  - Timestamps are formatted `yyyy-MM-dd'T'HH:mm:ss.SSS'Z'`.
- The queries assume **GraphDB-specific behaviour** in four places. Each one
  needs a decision (§4):
  1. **Inferred `snvoc:directKnows`.** A custom GraphDB rule
     (`rule_snb_knows_bidirectional`) derives a symmetric `directKnows` from the
     reified `knows` node. 14 of the 21 reads use it. The data contains none.
  2. **Ontotext path search.** `SERVICE <http://www.ontotext.com/path#search>`
     wraps a nested `SERVICE <urn:path>`. It appears in five queries:
     - IC1: distance, at most 3 hops;
     - IC6: all paths, at most 2 hops;
     - IC11: shortest path, at most 2 hops;
     - IC13: distance, unbounded;
     - IC14: shortest paths, unbounded.
  3. **Ontotext function** `ofn:minutesBetween` (IC7).
  4. **Projection alias reuse.** `(SUM(?x) AS ?a) (?a + ?b AS ?t)` (IC3).
     `pyoxigraph` rejects it ("The SELECT contains an expression with a variable
     that is unbound"). GraphDB accepts it.

### 2.3 Data

- **Source:** the Hadoop Datagen's `Turtle*Serializer`, pre-generated by LDBC.
  The download URL is
  `https://datasets.ldbcouncil.org/snb-interactive-v1/social_network-sf{SF}-Turtle.tar.zst`.
- **Scale factors available in Turtle:** 0.1, 0.3, 1, 3, 10, 100, 300 and 1000.
  **There is no SF0.003 Turtle.** SF0.1 is the smallest; the sister project's CI
  scale does not exist here.
- **SF0.1, measured 2026-10-23:**
  - 27.3 MB compressed (SHA-256
    `7bc10912d0844be4240de3ca648cc4282b4a29a0be6dc3872f3ce52cdf05485e`);
    three files: static 7.3 MB, person 9.1 MB, activity 240.6 MB.
  - **4,028,511 triples.** `pyoxigraph` bulk-loads them in about 5 s, at about
    2.2 GB peak RSS on a developer laptop.
  - Classes: Person 1,528 · Forum 13,750 · Post 135,701 · Comment 151,043 ·
    Tag 16,080 · TagClass 71 · Place 1,459 (City 1,343, Country 111,
    Continent 6) · University 6,380 · Company 1,575.
- **SF1:** 342.5 MB compressed.
- **Shape facts that drive the design (counted on SF0.1):**
  - **Relationships with properties are reified as blank nodes:**
    - `knows` (14,073), stored in **one direction only**: 0 symmetric pairs;
    - `hasMember` (123,268);
    - `likes` (109,440): 47,215 point to a Post via `hasPost`, 62,225 to a
      Comment via `hasComment`;
    - `studyAt` (1,209) and `workAt` (3,313).
  - **251,374 blank-node subjects** in total. They include the 71 tag classes
    (`_:tagclassNNN`), which carry an `rdfs:subClassOf` hierarchy. Tags are
    typed by them: `sntag:Rumi rdf:type _:tagclass000211`.
  - **Multi-typed nodes:** all 1,459 places are both `dbpedia-owl:Place` and one
    of `City` / `Country` / `Continent`.
  - **No `Message` class.** Posts and Comments are separate classes. The queries
    reach messages through untyped variables (`?m snvoc:hasCreator ?p`) that
    range over both.
  - Static entities use DBpedia IRIs (`dbpedia:India`).
- **Substitution parameters** are official:
  `snb-interactive-v1-parameters/substitution_parameters-sf0.1.tar.zst`
  (203 KB).

### 2.4 Correctness oracles

1. **`pyoxigraph`.** The W3C ground truth (AGENTS.md hard rule 5) runs the
   *same SPARQL text* on the *same normalised data*. It is in-process and needs
   no Docker.
2. **LDBC validation parameters.** LDBC publishes expected results for
   Interactive v1 at SF0.1–SF10:
   `interactive-v1/validation_params-interactive-v1.0.0-sf0.1-to-sf10.tar.zst`
   (205 MB). They were produced by the Neo4j reference implementation. They
   validate the **SPARQL text itself**: a variant that disagrees with them is a
   bad variant, not a translator bug.
   - Note for the sister plan: its §2.4 says LDBC does not publish validation
     files. That holds for v2, not for v1.
   - **Checked 2026-10-24: not usable as they stand.** The SF0.1 file
     (`validation_params-sf0.1.csv`, 138,474 lines) interleaves **18,626
     updates with 119,848 reads, starting on its first line**. Each expected
     answer describes the database *after* the inserts before it, which the
     Turtle snapshot does not contain (the first short read already returns
     a comment the first line inserts). Using them means replaying those
     updates on the oracle store first — pyoxigraph supports SPARQL Update,
     and the reference `interactive-update-*.rq` templates exist — which is
     follow-up work package WP-LDBC-REPLAY. **Until then pyoxigraph is the
     only oracle**, and the `oracle_disagrees` state is unused.
   - **Replay, increment 1 (2026-10-30).** `python -m tests.ldbc.replay`
     applies each insert to a copy of the normalised oracle store, in file
     order, and checks the first *N* reads of each short read at their
     point in the stream. The inserts are written to match the Turtle model,
     not taken from the reference `interactive-update-*.rq` templates (those
     reuse an existing `studyAt` / `workAt` node). At SF0.1, 50 each of IS1–IS5
     and IS7 agree with LDBC (300/300): the short reads' SPARQL text and the
     normalisation are right. IS6 is left out by default: pyoxigraph does
     not answer it within 10 minutes and has no query timeout. Complex reads
     and replaying the inserts on the ArangoDB layouts are the next
     increments.

The two oracles separate the failure classes cleanly (once both exist):

| Disagreement | Means |
| --- | --- |
| `pyoxigraph` ≠ LDBC validation | The query text, a variant or the normalisation is wrong. Not a translator bug. |
| ArangoDB ≠ `pyoxigraph` | The translator (or a mapping fixture) is wrong. |

## 3. Baseline probe (2026-10-23, no code changes)

Every read query was translated with `arango_sparql.api.translate()` after
splicing sample parameters. Three **provisional** ontologies were used:

- **PG:** one collection per class;
- **LPG:** `vertices` + `type`;
- **RPT:** `_triples`.

They declared **classes only**: no properties, no edges, no reified-node
mappings. The probe script lives outside the repo; WP-LDBC-CORPUS makes it a
committed, ratcheted test with faithful mappings.

### 3.1 Translation outcome (21 reads)

The outcome was identical in all three layouts, because the provisional
mappings carried no layout-specific property information:

| Outcome | Count | Queries | Cause |
| --- | --- | --- | --- |
| Translates | 11 | IS1–IS5 IS7 IC2 IC4 IC8 IC9 IC12 | — |
| `SparqlParseError` | 5 | IC1 IC6 IC11 IC13 IC14 | rdflib 7.6.0 recurses without bound on a `SERVICE` nested inside a `SERVICE` (minimal reproduction: `SERVICE <a> { … SERVICE <b> { … } }`). The message we surface is "maximum recursion depth exceeded". |
| `UnsupportedSparqlError` | 4 | IS6, IC5 (cross-subject `OPTIONAL`); IC10 (`OPTIONAL` whose body is `Extend`); IC7 (`ofn:minutesBetween`) | Translator gaps, failing closed. |
| Correctly refused | 1 | IC3 | Projection alias reuse. `pyoxigraph` rejects it too, so this needs a variant, not a fix. |

### 3.2 "Translates" is not "correct"

The probe found a **silent-wrong** defect, which is why execution against an
oracle is mandatory:

- **`xsd:dateTime + xsd:duration` silently becomes `null`.**
  - The arithmetic lowers to a numeric-only guard:
    `IS_NUMBER(a) && IS_NUMBER(b) ? a + b : null`.
  - So `FILTER(?d < ?end)` compares against `null` and drops every row,
    without an error.
  - The duration is bound as a Python `timedelta`. That is not
    JSON-serialisable, so execution would fail at the driver rather than in
    translation.
  - IC4 "translates" this way, and IC3 would once its variant exists.

The 11 "translates" are therefore an **upper bound**. With faithful mappings,
some will move to `fails_closed` and some may turn out `translates_wrong`. Only
the ledger (WP-LDBC-CORPUS) and execution (WP-LDBC-ORACLE) can tell.

### 3.3 What implementation found (2026-10-24)

The harness (WP-LDBC-DATA, -CORPUS, -PARAMS, the pyoxigraph half of
-ORACLE) is built; `tests/ldbc/conformance_ledger.tsv` is the live record.
What it found, beyond §3.1, §3.2 and §3.4:

- **Faithful baseline: 0 of 26 texts translated on any layout** under the
  live service's strict resolver, every one failing closed (no crash, no
  wrong AQL). The dominant cause was untyped subjects: the LDBC queries
  rarely write `?m a :Post`.
- **Fixed — RDF layout reads untyped subjects** (commit `e65b072`). In a pure
  triple store (every class RPT on one table) a constant or untyped
  subject is read from the triples table, and property paths compose.
  RDF layout: 0 → 15 of 26 texts translate.
- **Fixed — silent wrong answer: `<x> a :C` ignored x in PG and LPG**
  (`9448c37`): it matched every member of :C. A production bug, not only an
  LDBC one.
- **Fixed — silent wrong answer: `dateTime ± duration`** (`f4bf7a2`), the
  §3.2 defect, confirmed live: lowered to `DATE_ADD` / `DATE_SUBTRACT`.
- **Fixed — join order was a performance defect** (`4a0455b`). The visitor
  emitted a BGP's triples in a fixed order (type patterns, then variable
  subjects, then constant subjects *last*), so IS1 scanned all 327 k
  `snvoc:id` rows before applying the person (1.4 s), and IS2 scanned all
  135 k posts per message (72–110 s). Triples whose subject is known now
  come first; IS1 takes 16 ms. Before/after timings are in the report.
- **Fixed — PG and LPG route subjects without type patterns** (`c068771`):
  `owl:SymmetricProperty` traverses `ANY` (decision D10), an unbound subject
  with a known object is reached by an `INBOUND` traversal, and a constant
  or value-bound subject opens its `rdfs:domain` class (an LPG union is an
  any-of label test). A PG union across collections reads each collection
  (D9, approved 2026-10-28): `FOR … IN UNION(…)`, one arm per collection with
  the constant subject's `_uri` match inside each arm. Live on PG: IS4, IS5,
  IC3 (no-alias-reuse) and IC4 now match the oracle (4 → 8 PG cells); IS2,
  IC8, IC9 and IC10 ran but exceeded the 3 GB query cap; IS6 runs but the
  oracle times out.
- **Fixed — performance: value-bound joins hid both indexes** (2026-10-29). A
  fresh scan joined to a variable that already had a value (a sub-select
  column, a VALUES row, a MINUS / EXISTS probe's outer row) filtered on
  `NOT_NULL(doc._uri, doc._id) == value`, scanning the whole collection per
  outer row; across a PG union the filter sat after the materialised `UNION`.
  The join is now `value != null && (doc._uri == value || (doc._uri == null
  && doc._id == value))` (`builder.subject_matches_value`), inside each union
  arm. IS2 (PG) went from the memory cap to 10 rows in 0.03 s; IS2 and IC8
  (PG) and IC3 (LPG) now match the oracle (all layouts 28 → 31, none wrong).
  IC9 (PG) still exceeds the cap and IC10 times out.
- **Fixed — OPTIONAL as a correlated subquery** (`3327f74`, `6a070b9`):
  ADR-0002 Option A generalised from one triple to any pattern (several
  triples, paths, BIND, an inner FILTER). Two NL-eval fixtures asserted the
  old refusals and were moved to permanent ones (federation, Update).
- **Fixed — silent wrong answer: path intermediates collided across child
  scopes** (`9c6af74`). Every UNION arm, OPTIONAL, MINUS / EXISTS probe
  and sub-SELECT restarted its `_path_<n>` counter while seeded with the
  outer bindings, so IC6 joined "friend of a friend" to the outer path's
  tag and returned 0 of 10 groups.
- **Oracle defects, not translator defects.** pyoxigraph (0.5.x up to 0.5.13)
  returns unbound for some valid `dateTime + duration` sums, and a FILTER on
  such a sum drops rows, so it was wrong for IC3 and IC4 while ArangoDB was
  right (checked row by row). The cause is its optimizer: it sorts the
  operands of `+` by hash, as if `+` were commutative, and its evaluator has
  no `duration + dateTime` case. Which sums fail depends on operand values and
  variable names (`"2012-01-01T00:00:00Z" + "P1D"` fails, `+ "P30D"` does
  not; `?v1 + "P1D"` fails, `?v2 + "P1D"` does not). The oracle folds the
  constant `dateTime + P<n>D` sums the corpus uses (`a17b0a8`) and refuses
  any other `+` of a duration literal. It also returns canonical
  dateTime forms (`…38.9Z` for `…38.900Z`), now compared as instants, and
  zero rows for a GROUP BY over no input where the W3C suite
  (`aggregates/agg-empty-group`) and the translator return one empty row.
- **pyoxigraph executes `SERVICE` over HTTP.** The GraphDB queries name
  `http://www.ontotext.com/path#search`; an early oracle run sent such
  requests before the oracle learnt to refuse `SERVICE`. It now refuses
  any query that mentions it.
- **pyoxigraph is slow on several shapes** (IS6, IC5, IC7 variant, IC9,
  IC10, IC12: over 120 s at SF0.1). Answers and timeouts are cached, and
  `python -m tests.ldbc.oracle --warm` computes them in parallel; a query it
  cannot answer within the limit is `oracle_unavailable`, never a pass.
- **The benchmark needs its own ArangoDB.** On a Docker VM shared with other
  containers, ArangoDB sizes its caches for the whole VM and was OOM-killed
  three times under the load, even with a per-query memory limit.
  `docker-compose.ldbc.yml` runs a memory-capped server (3 GB, told its cap)
  on port 8533.
- **Found by the first full live run (2026-10-26).** No query returned a
  wrong answer, but two raised AQL errors, and both were translator
  defects:
  - **Fixed — silent wrong answer: an unprojected GROUP BY variable was not
    a key** (`d805071`). rdflib synthesises a Sample only for the GROUP BY
    variables a query projects, and the COLLECT keys came from those
    alone, so IC5's `GROUP BY ?title ?forum` (projecting `?title`) merged
    forums that share a title, and `GROUP BY STR(?d)` grouped nothing. IC5
    only surfaced it because its ORDER BY read `?forum` after the COLLECT
    (ArangoDB: "collection or view not found: row9"). A production bug.
  - **Fixed — UNION and OPTIONAL arms re-read outer documents**
    (`b74d544`). A child scope received an outer PG/LPG subject as an IRI
    only, so each arm scanned the subject's domain and joined back on the
    IRI. Arms now traverse from the outer document; IC2 on PG translates
    and matches the oracle.
  - **ArangoDB defect, fixed in 3.12.12: IS6 on LPG.** ArangoDB 3.12.9 rejects
    valid AQL with an internal error (`ERR 4`, "missing variable doc1 …
    for node … (TraversalNode) while planning registers … Please report
    this error"). It needs four optimizer rules together (disabling any
    one of `use-indexes`, `optimize-traversals`,
    `batch-materialize-documents`, `optimize-projections` avoids it); the
    reduced query is an outer document used both in a UNION subquery with
    a traversal and in a later LET. A standalone script with synthetic data
    reproduces it on 3.12.9 and not on 3.12.12, the current release; the
    benchmark now runs on 3.12.12.
- **Fixed — regression caught by the W3C live gate: a reverse traversal
  returned duplicates** (`07af466`). Walking an edge backwards (`c068771`)
  reached a second copy of the same IRI in another collection (the W3C
  loader stores a typed resource in `Document` and in its class
  collection), so `sparqldl-07/08/09` returned their answer twice. The
  vertex is now kept to the collections the forward plan reads, with the
  tenant filter the forward plan's class would have.
- **The benchmark runner crashed on the first EXPLAIN error** and looked
  up pyoxigraph times under the wrong cache key; both fixed (`a17b0a8`).

### 3.4 Upstream issues (status 2026-10-26)

- **rdflib:** unbounded recursion on nested `SERVICE` (`parseQuery`, 7.6.0).
  Already reported (RDFLib/rdflib#2136, #3082) and fixed on rdflib's main by
  RDFLib/rdflib#3608 (merged 2026-10-22), not yet released. On our side the
  `RecursionError` now maps to a stable `E_SPARQL_UNSUPPORTED` that names
  nested `SERVICE` (`translate/parser.py`, with an upstream marker) instead of
  a parse error, until a release carries the fix.
- **LDBC:** IC3's alias reuse is not portable SPARQL 1.1. Not reported: LDBC
  removed the SPARQL implementations from `ldbc_snb_interactive_v1_impls`
  (issue #163), so the pinned commit `11db98c` is the last SPARQL reference.
- **ArangoDB:** the IS6 planner error (§3.3) is fixed in 3.12.12; nothing to
  report.
- **pyoxigraph:** unbound `dateTime + duration` sums (§3.3), still present in
  0.5.13 (the current release). oxigraph's `main` no longer reorders `+`
  (`a941f10`, a refactor, unreleased); the one-line fix for the `0.5` branch,
  with a regression test, is prepared but not yet proposed upstream. The
  oracle folds constant sums until a release carries it.

## 4. Scope decisions (recommendations for review)

| # | Decision | Recommendation | Alternatives |
| --- | --- | --- | --- |
| D1 | Workload | **SNB Interactive v1 reads: IS1–IS7 and IC1–IC14.** These are the only SNB queries with a SPARQL reference. | Write SPARQL for v2 or BI ourselves. Rejected: that hides exactly the gaps we want to find, and the text would have no independent author. |
| D2 | Physical layouts | **RDF (`RPT` `_triples`), LPG (`LABEL` + `GENERIC_WITH_TYPE`) and PG (`COLLECTION` + `DEDICATED_COLLECTION`), all three mandatory.** PG and LPG follow the LDBC property-graph schema, using **the sister project's collection names**, so one loaded database serves both transpilers (WP-LDBC-XTRANS). Hybrid is optional, in Phase 3. | ArangoRDF's PGT/LPG loaders. Rejected: ArangoRDF's "RPT" is statement-as-edge, not our `_triples` table, and its PGT keeps reified nodes as vertices. |
| D3 | Query text | **Vendor the GraphDB `.rq` files verbatim**, pinned to `11db98c`, and never edit them. Adaptations go in `variants/<op>.<reason>.rq`, each with a header comment saying what was changed and why. The ledger reports verbatim and variant outcomes separately. Planned variants: IC1, IC6 and IC11 (bounded path search rewritten as standard `UNION` / sequence paths); IC3 (no alias reuse); IC7 (standard date arithmetic in place of `ofn:minutesBetween`). | Rewrite everything into a portable subset. Rejected for the same reason as D1. |
| D4 | Data normalisation | **One `normalize` step over the published Turtle produces the dataset that every target loads** (`pyoxigraph`, RPT, LPG, PG). It does exactly two things: (a) materialise symmetric `snvoc:directKnows`, which is GraphDB's custom rule and the only inference the queries depend on (28,146 triples at SF0.1); (b) skolemise blank nodes into `/.well-known/genid/` IRIs (RDF 1.1 §3.5), so PG and LPG documents have stable keys and results compare across stores. The output is checksummed. Inference is therefore not under test. | Teach the translator RDFS / custom-rule inference. Out of scope for this product. |
| D5 | Oracles | **Two, both automated** (§2.4). `pyoxigraph` runs live in the harness; it is pinned in `uv.lock` and deterministic, so **no snapshots are committed**. LDBC validation parameters check the SPARQL text, and their disagreement is a separate ledger state (`oracle_disagrees`). | Snapshots, as in the sister plan. Unnecessary here: our oracle is in-process and needs no Neo4j container. |
| D6 | Data in repo | **Download on demand with SHA-256 pins**, cached under `~/.cache/arango-sparql/ldbc/` and by `actions/cache` in CI, as `scripts/fetch_w3c.sh` does for the W3C suite. Only mappings, parameters, the manifest and the ledger are committed. | Vendor a subset. Rejected: no generated or vendored data in the repo (AGENTS.md *Off-limits*). |
| D7 | Scale factors | **SF0.1 nightly** (correctness + performance), **SF1 manual**, SF3/SF10 ad hoc on dedicated hardware. **Per PR: the translation ratchet only**, which needs no data. | A per-PR live tier on a deterministic SF0.1 subgraph (open question 6). |
| D8 | Reified relationships (**the biggest design choice**) | **A new mapping construct, "relationship node ↔ edge document".** The reified node binds to the edge document (PG: `knows` edge collection; LPG: `edges` filtered on `type`). The entry predicate (`snvoc:knows`) reads `_from`. The exit predicate (`snvoc:hasPerson`) reads `_to`. The node's datatype properties (`creationDate`) are edge attributes. So `?p :knows ?k . ?k :hasPerson ?f . ?k :creationDate ?d` lowers to one `FOR f, k IN OUTBOUND p @@knows`. **The vocabulary is proposed upstream in `arango-schema-analyzer`**, which owns the `phys:` namespace. Its conceptual model already carries relationship `attributeFields`, but its OWL export drops them. | (a) Load reified nodes as vertices plus two edges. Honest, but that is not the PG that customers or the sister project have. (b) SPARQL-star `<< ?p :knows ?f >> :creationDate ?d`. Rejected: rdflib does not parse it (verified), and hard rule 1 forbids another parser. |
| D9 | Polymorphic domains and multi-typed nodes | **Resolver lowering from `rdfs:domain` / `rdfs:range`**, including the `owl:unionOf` domains the analyzer already emits. An untyped subject whose properties belong to Post ∪ Comment scans **both** PG collections: a union of member collections for a scan start, and the natural multi-collection target for a traversal. LPG uses the shipped labels array (`typeFieldIsArray`, issue #10). **Coordinate with the sister plan's D8** (supertypes in `arango-query-core`): it is the same conceptual need, so there should be one upstream model, not two. Until it lands, an ambiguous subject MUST fail closed rather than scan a default collection. | Make polymorphism LPG-only and have PG fail closed. |
| D10 | `directKnows` in PG and LPG | **Declare `snvoc:directKnows` an `owl:SymmetricProperty` mapped onto the `knows` edge collection, traversed `ANY`.** This is standard OWL, needs no duplicated data, and matches Neo4j's undirected `-[:KNOWS]-`. RPT keeps the materialised triples from D4. | Materialise a `directKnows` edge collection (twice the `knows` edges). Simpler, but it measures data duplication instead of the translator. |
| D11 | Performance comparison | Report, per query × layout × SF: translation time (cold and warm) and AQL execution p50/p95/p99 (server-side) with an `EXPLAIN` plan digest. `pyoxigraph` timings appear as an **indicative** in-process RDF-engine reference, with the disclaimer. **Report-only** (PRD §9.4 tiering); never CI-blocking. | ArangoDB only. Or add GraphDB running the verbatim queries: its free licence's benchmark-publication terms need checking first. |

## 5. Architecture

### 5.1 Layout (mirrors the `tests/w3c/` precedent)

```
tests/ldbc/
  UPSTREAM.md              # repo URLs, pinned commits, licence, refresh procedure
  NOTICE                   # Apache-2.0 attribution for the vendored queries
  queries/
    interactive_v1/        # verbatim *.rq (21 reads)
    variants/              # <op>.<reason>.rq, each with a header comment
  manifest.yml             # op → file, parameters, result columns, ordering contract, variants
  datasets.py              # fetch + SHA-256 + cache (SF → URL, digest)
  normalize.py             # directKnows materialisation + skolemisation + output digest
  loader.py                # normalised RDF → ArangoDB RPT | LPG | PG
  params.py                # official substitution parameters → bindings (+ one empty-result binding per op)
  oracle.py                # pyoxigraph runner + LDBC validation-parameter reader
  ledger.py                # computes outcomes → conformance_ledger.tsv
  conformance_ledger.tsv   # op × layout × {parse, translate, execute, oracle}
  test_ldbc_ratchet.py     # default suite: translation tier, no DB, < 5 s
  test_ldbc_execution.py   # integration: execute on ArangoDB + compare to pyoxigraph
  test_ldbc_validation.py  # integration: pyoxigraph vs LDBC validation parameters
  replay.py                # LDBC's update stream on the oracle, short reads vs LDBC (WP-LDBC-REPLAY)
  bench.py                 # perf runner: python -m tests.ldbc.bench --sf 0.1 --layout rpt,lpg,pg
  report.py                # results JSON → docs/ldbc_results.md (with disclaimer)
tests/ldbc/mappings/
  ldbc_rpt.ttl  ldbc_lpg.ttl  ldbc_pg.ttl   # committed OWL mapping fixtures (the contract)
scripts/fetch_ldbc.sh      # same shape as scripts/fetch_w3c.sh
```

### 5.2 The outcome model

Each operation × layout records four passing steps:

1. `parses`
2. `translates`
3. `executes`
4. `matches_oracle`

There are four terminal non-passing states. Each must state its reason:

| State | Meaning |
| --- | --- |
| `fails_closed` | An explicit `UnsupportedSparqlError`, with a stable code. The acceptable failure. |
| `translates_wrong` | ArangoDB ≠ `pyoxigraph`. A **defect**, and it outranks every unsupported feature (PRD §6, AGENTS.md workflow 5). |
| `out_of_subset` | The verbatim text uses a vendor extension (Ontotext path search, `ofn:`) with no standard equivalent. |
| `oracle_disagrees` | `pyoxigraph` ≠ LDBC validation: a query-text or normalisation defect. |

The ratchet fails CI if any cell **leaves** a passing state, or an improvement
goes unrecorded. A `translates_wrong` cell can never be grandfathered as
passing.

### 5.3 Result comparison

- Reuse `tests/helpers/oxi.py`: `assert_bindings_equal`,
  `assert_bindings_equal_ordered` and `normalize_oxi_row`. Do not copy them.
  Extend them if LDBC needs more: for example, `xsd:long` against JSON number
  folding, and `GROUP_CONCAT` order (which SPARQL leaves undefined, so we
  compare it as a set).
- **Ordering contract.** `manifest.yml` marks each query's ordering as total or
  not. Compare *ordered* only when it is total. Otherwise compare as a multiset.
  The manifest records this per query, from a reading of each `ORDER BY`.
- The reads project literals and IDs, never whole nodes. Skolemised IRIs are
  compared as IRIs.

### 5.4 Loader

The loader streams the normalised Turtle with `pyoxigraph`'s parser; it never
builds an in-memory rdflib graph.

**RPT.** One `_triples` collection, in the PRD §6.1 shape:
`subject_uri`, `predicate`, `object_uri` / `object_value`. Indexes:
`[subject_uri, predicate]`, `[predicate, object_uri]` and
`[predicate, object_value]`.

**PG.** The LDBC property-graph schema, with collection names aligned to the
sister project's `ldbc_pg` fixture:

- One vertex collection per concrete class.
- One edge collection per relationship, `DEDICATED_COLLECTION`:
  - object properties become plain edges;
  - reified relationships (`knows`, `hasMember`, `likes`, `studyAt`, `workAt`)
    become edges carrying their attributes.
- Every document carries `_uri`, the RDF IRI, so constant subjects match
  (PRD §6.1, subject identity). `_key` comes from `snvoc:id`.

**LPG.** The same graph in one `nodes` collection and one `edges` collection:

- Each node gets `type` (its concrete class) and `labels`, an array of all its
  classes. This covers multi-typed places.
- Each edge gets `type`.
- `_key` is `<Class>_<id>`, because IDs collide across classes.

**Indexes (PG and LPG)** mirror the reference DDL: unique `id`, `firstName`,
`name`, `creationDate`. LPG also gets `labels[*]` and `edges.type` indexes.

**Integrity.** The loader is idempotent and reports counts per entity and per
relationship. It asserts **RDF == RPT == LPG == PG** for every class and
relationship. A mismatch fails loudly; nothing is dropped silently.

### 5.5 Mapping acquisition is also under test

After loading, the harness runs schema acquisition (`/schema/introspect`,
analyzer-backed) against each layout. It **diffs the acquired mapping against
the committed fixture.** The fixture is the contract. A difference is either an
analyzer defect (filed upstream against `arango-schema-analyzer`) or a fixture
error.

This also measures whether the analyzer can detect reified relationships and
polymorphic domains on a real graph. Today we expect it cannot (D8, D9).

## 6. Work packages

Sizes: **S** ≤ 2 days · **M** ≤ 1 week · **L** 1–2 weeks. ⚡ marks the
critical path. Each WP ships as one to three PRs of five files or fewer, each
green on its own (incremental over atomic).

### Phase 0 — Harness and baseline (no translator changes beyond fail-closed guards)

#### WP-LDBC-DATA: data sets, normalisation and loader ⚡ (M)
- **Scope:** `datasets.py` + `scripts/fetch_ldbc.sh`, `normalize.py` (D4) and
  `loader.py` (§5.4).
- **Tests:**
  - Unit tests for normalisation and loading on a hand-written Turtle snippet in
    LDBC shape, written by us rather than vendored. It covers a reified `knows`,
    a multi-typed place, a blank-node tag class and a `likes` to both Post and
    Comment.
  - An integration test that loads SF0.1 into all three layouts and asserts the
    §2.3 counts and the cross-layout count parity.
  - An idempotence test: load twice, same counts.
- **Acceptance:** `pytest -m integration tests/ldbc -k load` is green. Load time
  and disk size per layout are recorded for SF0.1.

#### WP-LDBC-CORPUS: corpus, mappings, ledger and fail-closed guards ⚡ (M)
- **Corpus:**
  - Vendor the 21 reads, with `UPSTREAM.md` and `NOTICE`.
  - Write `manifest.yml`.
  - Write the variants listed in D3.
- **Mapping fixtures:** `ldbc_rpt`, `ldbc_lpg` and `ldbc_pg`. Constructs that
  are not supported yet (reified edges, D8; polymorphic domains, D9) are
  declared so that they **fail closed**, not so that they translate.
- **Ledger:** `ledger.py`, `conformance_ledger.tsv` and `test_ldbc_ratchet.py`
  (default suite, no DB).
- **Fail-closed guards (the first translator change; each lands with a golden):**
  - `xsd:dateTime ± xsd:duration` raises `E_SPARQL_UNSUPPORTED` instead of
    lowering to `null` (§3.2).
  - The nested-`SERVICE` `RecursionError` maps to a stable error that names
    `SERVICE` (done 2026-10-29). The rdflib issue already existed
    (RDFLib/rdflib#3082); the fix is #3608.
  - Any further `translates_wrong` cell the faithful-mapping ledger exposes.
- **Acceptance:** the ratchet runs in under 5 s, and the ledger reproduces §3.1
  with faithful mappings.

#### WP-LDBC-ORACLE: oracles and execution tier ⚡ (M)
- **Scope:**
  - `oracle.py`: a `pyoxigraph` runner on the normalised data, using an
    on-disk store so the 5 s load is paid once.
  - An LDBC validation-parameter reader.
  - `test_ldbc_execution.py` (ArangoDB × 3 layouts vs `pyoxigraph`) and
    `test_ldbc_validation.py` (`pyoxigraph` vs LDBC).
- **Verify first** that the validation parameters, generated from the CSV
  serialisation of Datagen v1.0.0, describe the same graph as the Turtle. Check
  entity counts and spot-check IDs. If they do not, `pyoxigraph` remains the
  sole oracle and variants lose their independent check. Report that as a
  finding.
- **Acceptance:**
  - All four outcome columns are populated for every op × layout.
  - A deliberately corrupted expected value makes the test fail. This is a
    mutation check, so the gate is shown not to be vacuous.

#### WP-LDBC-PARAMS: substitution parameters (S)
- **Scope:** `params.py` reads the official `substitution_parameters-sf0.1` and
  takes the first N bindings per operation, deterministically. It also adds one
  empty-result binding per operation, because the empty case is an edge case
  too. Parameters are passed as SPARQL text, the way the reference expects; see
  open question 7.
- **Acceptance:** at least 3 bindings per read, and byte-identical regeneration.

**Milestone M1 (end of Phase 0).** We have a reproducible, ratcheted baseline
for 21 reads × 3 layouts at SF0.1, and every failure is filed as an issue
labelled `ldbc`. This alone yields a correctness report.

### Phase 1 — Correctness gaps, ordered by queries unlocked

The M1 ledger sets the final order. These are the gaps known today:

#### WP-LDBC-EDGENODE: reified relationships as edge documents ⚡ (L)
- **Upstream (`arango-schema-analyzer`):**
  - Propose the D8 `phys:` vocabulary.
  - Export relationship `attributeFields` in the OWL.
  - Bump the pin here. Any interim workaround carries an `# upstream:` marker.
- **Translator:**
  - Bind the reified variable to the edge document.
  - Lower the entry and exit predicates to `_from` / `_to`.
  - Read node properties as edge attributes.
  - Support the symmetric `ANY` traversal for D10.
- **Tests:** goldens in both PG and LPG, and a `pyoxigraph` cross case per
  shape.
- **Unlocks:** IS3, IC1, IC5, IC7 and IC11 on PG and LPG, plus all 14
  `directKnows` queries through D10.

#### WP-LDBC-POLY: polymorphic domains and multi-typed nodes ⚡ (L)
- **Scope:**
  - The D9 lowering: Post ∪ Comment, the Place members, and the Organisation
    members.
  - Shared design with the sister project's WP-35 (`arango-query-core`).
  - Fail closed until it lands.
- **Unlocks (PG):**
  - every query that reaches messages through `hasCreator` on an untyped
    variable: IS2, IS5, IS7, IC2–IC10, IC12 and IC14;
  - IS4–IS7, which take a message ID that may name a Post or a Comment. A
    constant subject routed by a union domain is now matched in each member
    collection (D9).

#### WP-LDBC-OPT: `OPTIONAL` on collection layouts (M)
- **Scope:**
  - Cross-subject `OPTIONAL` on PG and LPG (IS6, IC5). This generalises
    ADR-0002's RPT-native option, using the correlated-subquery pattern from
    issue #48.
  - `OPTIONAL` bodies containing `BIND` / `EXISTS` (IC10, IC14).

#### WP-LDBC-PATHS: property paths at LDBC depth (M)
- **Scope:**
  - Property paths over RPT subjects, a documented gap in
    `translate/paths.py`.
  - `*` / `+` over edge collections (IS2, IS6 `replyOf*`; IC14).
  - IC12's tag-class typing (`rdf:type/rdfs:subClassOf*` on class *nodes*).
    For PG and LPG, add a labelled IC12 variant over `hasType` / `isSubclassOf`
    edges; the verbatim text stays `fails_closed` there.

#### WP-LDBC-TEMPORAL: date arithmetic (M)
- **Scope:**
  - Lower `xsd:dateTime ± xsd:duration` to `DATE_ADD(d, "P30D")`; AQL accepts
    ISO-8601 durations. Bind durations as ISO strings.
  - Lower dateTime differences, for the IC7 variant, to `DATE_DIFF`.
  - Compare timestamps in one canonical encoding: ISO-8601 UTC with
    millisecond precision, as the Turtle stores them. Constants are normalised
    to the same form, so string comparison cannot go wrong at a precision
    boundary.
- **Unlocks:** IC3 and IC4; replaces the guard from WP-LDBC-CORPUS.

**Milestone M2.** Every read except IC13 and IC14 reaches `matches_oracle` on
**all three** layouts, counting the IC1, IC3, IC6, IC7 and IC11 variants.

### Phase 2 — Performance

#### WP-LDBC-BENCH: runner and report (M). It can start right after M1, on whatever passes.
- **Measurements:**
  - **Translation:** `translate()` cold and warm, p50/p95 per op. Compare
    against the PRD §9.4 `/translate` budgets on real queries.
  - **Execution:** per op × layout × SF. Discard K warm-up runs, then take
    N bindings × R repeats.
  - **Per run:** p50/p95/p99, row count, server-side `executionTime` from cursor
    stats, and a per-query timeout recorded as `TIMEOUT`.
  - **Plan digest:** from `EXPLAIN`, so plan regressions are diffable.
  - **Reference:** `pyoxigraph` timings on the same text (indicative, D11).
- **Environment capture:** ArangoDB version and image digest, CPU, RAM and
  container limits, SF and normalised-data digest, git SHA, and the
  mapping-fixture hash.
- **Output:**
  - `results/<date>-<sf>-<host>.json`, a CI artefact that is not committed.
  - `docs/ldbc_results.md`, generated by `report.py`. It carries the §2.6
    disclaimer, and a conformance test checks every number in it against a
    committed summary JSON, so the prose cannot drift.
- **CI:** an `ldbc-bench.yml` workflow, `workflow_dispatch` for SF0.1 and SF1,
  plus an optional non-blocking nightly at SF0.1.

#### WP-LDBC-OPTIMIZE: optimisation loop (L, open-ended)
- **Scope:** triage the slowest op per layout from the plan digests. Expected
  hot spots:
  - RPT `_triples` self-joins (index choice);
  - PG polymorphic unions;
  - LPG type filters;
  - unbounded `replyOf*` walks.
- **Each fix** lands as a translator change with a golden plus a plan-shape
  assertion, and adds a before/after row to the report with a regression bound.

### Phase 3 — Optional

- **WP-LDBC-XTRANS: cross-transpiler comparison.** `arango-cypher-py` runs the
  Interactive v1 reference Cypher, from the same commit `11db98c`, on *our* PG
  and LPG load. That gives one database, one LDBC oracle, and SPARQL→AQL against
  Cypher→AQL on correctness and on time. It is cheap only if D2's collection
  names are aligned from the start.
- **WP-LDBC-HYBRID: a hybrid layout.** Static data (places, tags, tag classes,
  organisations) in RPT, dynamic data in PG. It exercises the PRD §3.4
  mixed-model BGP on a real graph. This is our differentiator.

## 8. Risks

| Risk | Mitigation |
| --- | --- |
| The SF0.1 RPT load (about 4 M documents) is slow in CI | Measure it in WP-LDBC-DATA. SF0.1 stays nightly; the per-PR tier needs no data. |
| `pyoxigraph` needs about 2.2 GB RSS at SF0.1 | It fits the 7 GiB runner. An on-disk store avoids reloading per test. |
| The LDBC validation parameters do not describe the Turtle graph | WP-LDBC-ORACLE verifies this first. The fallback is `pyoxigraph` alone, reported as a finding. |
| A variant changes the semantics | LDBC validation catches it (`oracle_disagrees`). Each variant is reviewed with its header comment. |
| The D8 vocabulary stalls upstream | The fixtures plus the fail-closed guards keep `main` safe; only the unlock waits. Any interim workaround carries an `# upstream:` marker. |
| The PG polymorphic union is slow | That is a finding, not a failure. Measure it against LPG (WP-LDBC-BENCH). |
| Probe numbers are optimistic | §3 says so; the ledger replaces them at M1. |
| Unaudited numbers are read as LDBC results | Generated reports carry the disclaimer, and a conformance test fails if it is missing. |

## 9. Out of scope / future

- **Update operations (IU1–IU8).** The service is read-only (PRD §5.2, §5.3).

- **NL → SPARQL.** The LDBC specification describes each query in English,

## 10. Open questions for review

1. **D8, reified relationships.** *Decided 2026-10-29:* the relationship node
   is the edge document. RDF 1.2's RDF-star is the same construct (a reifier
   node), so only the query syntax differs; the LDBC n-ary form ships now
   (`phys:reifiedEdge` entry, `phys:edgeTargetOf` exits; PRD §6.1) and SPARQL
   1.2 syntax maps onto it once rdflib parses it. `rdf:Statement` is not
   accepted. The vocabulary is proposed upstream in `arango-schema-analyzer`.
2. **D9, polymorphism.** Share one upstream model with the sister plan's
   supertype work (`arango-query-core`), or keep the SPARQL resolver
   self-contained?
3. **D10, `directKnows`.** Symmetric `ANY` traversal of `knows`, or a
   materialised `directKnows` edge collection?
4. **IC13 / IC14.** Leave them `out_of_subset`, or design a vendor extension
   that lowers to AQL `SHORTEST_PATH` / `K_SHORTEST_PATHS`? If we design one,
   should it be Ontotext's `path:search` (which rdflib cannot parse today when
   nested) or our own function?
5. **WP-LDBC-XTRANS.** Align the PG and LPG layouts with the sister project now?
   Should the sister project also run v1, where LDBC publishes validation
   parameters?
6. **Per-PR live tier.** Translation ratchet only, or also a deterministic SF0.1
   subgraph executed on the existing `integration` CI job?
7. **Parameters.** The reference splices parameters as text. Should the harness
   also run a bind-parameterised form of each query, to measure the
   query-plan-cache effect? It would be a second labelled variant.
8. **Targets.** Should M1 and M2 become PRD §3 success criteria (for example,
   "v1.1: LDBC Interactive v1 reads match the oracle on RPT, LPG and PG")?
9. **Performance hardware and publication.** Where do SF1 and SF10 run, and on
   which ArangoDB baseline (3.11 or 3.12)? Is `docs/ldbc_results.md` acceptable
   in the public repo with the fair-use disclaimer?
